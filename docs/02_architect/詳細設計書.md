# EIAI TEC 公式サイト構築 詳細設計書

## 1. 文書情報

- 作成日: 2026-09-10
- 版数: v1.1(初回イテレーション)
- 参照元: `docs/02_architect/基本設計書.md` v1.0(2026-09-10)

## 2. 対象範囲

本書は基本設計書で定めた画面設計・システム構成をもとに、機能仕様書F-01〜F-11の実装レベルの詳細(入力項目定義、処理フロー、クラス設計、DB設計、API/インターフェース設計、エラーハンドリング)を定める。F-11(Vercelデプロイ・独自ドメイン設定)は運用・インフラ設定作業が中心であるため、4章に手順として記載するに留め、画面詳細設計・クラス設計の対象外とする。

## 3. 画面詳細設計

対象画面は基本設計書4章の3画面(4.1 トップページ、4.2 モバイルナビゲーション、4.3 フォーム送信結果表示)。本サイトで入力を受け付けるのはお問い合わせフォーム(F-07)のみであるため、入力項目定義表は同フォームについてのみ作成する。

### 3.1 入力項目定義表(Contactフォーム / F-07)

| 項目名(論理名) | UI要素 | 型・桁数 | 必須/任意 | 初期値 | バリデーション |
|---|---|---|---|---|---|
| 会社名・屋号(company) | `<input type="text">` | 文字列、最大100文字 | 任意 | 空文字 | 最大文字数超過時のみエラー(未入力は許容) |
| お名前(name) | `<input type="text">` | 文字列、1〜100文字 | 必須 | 空文字 | 未入力エラー、最大文字数超過エラー |
| メールアドレス(email) | `<input type="email">` | 文字列、1〜254文字(RFC 5321のパス長上限に準拠) | 必須 | 空文字 | 未入力エラー、`type="email"`によるブラウザ標準形式チェックに加え、サーバー側でも簡易な正規表現形式チェックを行う(`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`程度の簡易チェック)、最大文字数超過エラー |
| ご相談内容(message) | `<textarea>` | 文字列、1〜2000文字 | 必須 | 空文字 | 未入力エラー、最大文字数超過エラー |
| ハニーポット欄(honeypot、UI上の項目名は`company_url`等の実在しそうな名称とする) | `<input type="text">`(CSSで視覚的に非表示。`position:absolute; left:-9999px; opacity:0; height:0; overflow:hidden`等) | 文字列 | 空欄であること | 空文字 | 値が1文字でも入っていた場合、通常のバリデーションエラーとせず、8章のとおり「成功したふり」で処理を打ち切る |

- 各項目のプレースホルダー文言は機能仕様書4章F-07のとおりとし、変更しない。
- ハニーポット欄には`tabIndex={-1}`・`aria-hidden="true"`・`autoComplete="off"`を付与し、キーボード操作・スクリーンリーダー利用者の操作導線に影響しないようにする(基本設計書7章アクセシビリティ方針)。

### 3.2 操作定義表

#### 3.2.1 トップページ(LP)全体(基本設計書4.1節)

#### 3.2.2 モバイルナビゲーションメニュー(基本設計書4.2節)

## 4. 処理フロー設計

### 4.1 F-01: ヘッダー・グローバルナビゲーション(PC表示)

1. `SiteHeader`コンポーネント(Server Component)が、ロゴ・3件のナビゲーションリンク(`#services` `#portfolio` `#about`)・「お問い合わせ」ボタン(`#contact`)を描画する。
2. 各リンクは通常の`<a href="#xxx">`要素とし、ブラウザ標準のアンカージャンプ機能(`scroll-behavior`はCSSで`smooth`指定)によりスクロール移動する。JavaScriptによる独自のスクロール制御は行わない。
3. ヘッダーは`position:sticky; top:0;`を適用し、スクロール時も画面上部に固定する(`mockup/index.html`のCSSをそのまま踏襲)。
4. ヘッダーの実高さをCSS変数`--header-h`に反映し、各セクションの`scroll-margin-top`に適用することで、固定ヘッダーによる見出しの隠れを防ぐ(`mockup/index.html`の`syncHeaderHeight()`関数のロジックを移植。`ResizeObserver`または`load`/`resize`イベントで再計算する)。
5. 画面幅640px以下では、CSSメディアクエリ(`@media (max-width:640px)`)により`nav.site-nav`を非表示にし、4.8節のモバイルメニューに切り替える。

### 4.2 F-02〜F-06 共通: eyebrow自動スケーリング処理

Hero/Services/Portfolio/About/Contactの各見出しブロックで共通して行う処理(`mockup/index.html`の`syncOne`関数を移植)。

1. 対象の組(eyebrow要素・eyebrowテキスト要素・見出しテキスト要素・scale値)を以下のとおり定義する。

   | 対象セクション | scale値 |
   |---|---|
   | Hero | `0.7` |
   | Services | `2/3` |
   | Portfolio | `1`(既定値) |
   | About | `1`(既定値) |
   | Contact | `1`(既定値) |

2. 計算式: `eyebrowの新フォントサイズ = 現在のフォントサイズ(px) × (見出しテキストの表示幅 ÷ eyebrowテキストの表示幅) × scale`
3. Services/Portfolio/About/Contactの4セクションについては、上記個別計算後、Servicesの計算結果のフォントサイズを基準値とし、Portfolio/About/Contactのeyebrowフォントサイズをこの基準値で上書きする(4セクション間でeyebrowの文字サイズを完全一致させるため。`mockup/index.html`の`matchGroups`ロジックを踏襲)。Heroは対象外(単独レイアウトのため)。
4. 上記処理は、フォント読み込み完了時(`document.fonts.ready`)・ページ読み込み完了時(`load`)・画面リサイズ時(`resize`)に再実行する。
5. 実装方針: 上記ロジックをカスタムフック`useEyebrowAutoScale`(クライアントコンポーネント内でのみ使用)として1箇所に実装し、各セクション見出しコンポーネントから共通利用する(5章クラス設計参照)。

### 4.3 F-02: ヒーローセクション

1. `HeroSection`(Server Component)が、確定コピー(機能仕様書4章F-02のとおり)をそのまま描画する。見出し中の「AI」「EI(感性)」は`<span class="accent">`で個別にマークアップしオレンジ強調する。
2. eyebrowテキストは`AI meets EI.`のみを表示する(`mockup/index.html`の実表示テキストを正とする。site-direction.md記載の長い文言は採用しない)。
3. 4.2節の共通ロジック(scale=0.7)により、eyebrowの文字サイズを見出し(`heroLine1`)の表示幅に合わせて自動調整する。
4. CTAボタン「相談してみる」(`href="#contact"`、`btn btn-primary`)、「実績を見る」(`href="#portfolio"`、`btn btn-ghost`)を描画する。
5. ヒーロービジュアルとして`work.png`を`next/image`で描画する(基本設計書5.3節)。

### 4.4 F-03: Servicesセクション

### 4.5 F-04: Portfolioセクション

1. `PortfolioSection`(Server Component)が、見出しブロック(説明文なし)とメタ事例カード1件を描画する。
2. カードの各項目(CASE番号・タイトル・ステータスタグ・説明文・4ステップ・フッター注記)は、コンポーネント内の定数として保持する(機能仕様書4章F-04のコピーをそのまま使用)。
3. CASE番号は文字列定数`"000"`として保持する。将来、実案件(`CASE / 001`)が追加された際は、以下のルールに従って改修する(本イテレーションでは実装対象外。機能仕様書4章F-04の番号ルールを踏襲した申し送り)。
   - 実案件追加時: `001`から連番のCASEカードを新規に追加する。
   - `001`追加と同時に、本メタ事例(`CASE / 000`)カードをPortfolioセクションから削除する。
   - 事例が2件以上になった場合は横スライド(カルーセル)表示に切り替える。カルーセルの実装方式は次イテレーション(実績専用ページ化)の設計時に確定する(本書のスコープ外)。
4. 装飾アイコン(`worker3.png`)の垂直中央揃えは4.6節のロジックを使用する。
5. 4.2節の共通ロジック(scale既定値1)を適用する。

### 4.6 セクションアイコンの垂直中央揃え処理(Services/Portfolio共通)

`mockup/index.html`の`centerSectionIcon`関数を移植する。

1. 対象行要素(`servicesHeadRow` / `portfolioHeadRow`)内の見出しブロック(`.section-head`)と装飾アイコン画像(`.section-icon-tall`)の座標を取得する。
2. 見出しブロックの垂直中心座標を`見出しブロックのtop + 見出しブロックのheight / 2`で求める。
3. アイコン画像の目標top座標を`見出しブロックの垂直中心 - アイコン画像のheight / 2`で求める。
4. アイコン画像の現在のtop座標との差分を`margin-top`として適用する。
5. この処理はページ読み込み完了時・リサイズ時に再実行する(4.2節と同じタイミング)。

### 4.9 F-07: お問い合わせフォーム送信(Resend連携)

#### 4.9.1 クライアント側処理(`ContactForm`)

1. `useActionState`(React 19)で`submitContactForm`(4.9.2節)をバインドし、フォームの`action`属性に設定する。
2. 各入力欄の値をコンポーネントの状態(制御コンポーネント、または`FormData`ベースの非制御コンポーネントのいずれでも可。実装時に決定)として保持する。
3. 送信ボタン押下時、ブラウザ標準のHTML5バリデーション(`required`属性、`type="email"`)に加えて、以下のクライアント側チェックを行う。
   - `name`が空文字でないこと
   - `email`が空文字でないこと(形式チェックは`type="email"`に委ねる)
   - `message`が空文字でないこと
   - 各項目が3.1節の最大文字数を超えていないこと
4. クライアント側バリデーションNGの場合、送信を行わず該当欄の直下にエラーメッセージを表示し、最初のエラー項目にフォーカスを移動する(8章参照)。
5. クライアント側バリデーションOKの場合、フォームを送信中状態(ボタンを`disabled`にし「送信中…」表示に変更)にし、Server Action(`submitContactForm`)を呼び出す。
6. Server Actionからの結果(`ContactFormResult`)を受け取り、4.3節(基本設計書)の状態遷移に従って成功/失敗メッセージを表示する。

#### 4.9.2 サーバー側処理(`submitContactForm` Server Action)

1. `FormData`から`company` `name` `email` `message` `honeypot`を取得する。
2. `honeypot`に1文字でも値が入っている場合、以降の処理(バリデーション・メール送信)を行わずに、通常の送信成功時と同一の`{status:"success"}`を返却して処理を終了する(スパム発信元に判定ロジックを悟らせないため)。
3. `validateContactInput`(5章参照)でサーバー側バリデーションを再実行する(クライアント側バリデーションはバイパス可能であるため、サーバー側でも必ず再検証する)。バリデーションNGの場合、`{status:"error", fieldErrors:{...}}`を返却し処理を終了する。
4. `buildContactEmail`(5章参照)で、入力内容からメールの件名・本文(テキスト/HTML)を組み立てる。
5. `getResendClient`(5章参照)で初期化したResend SDKクライアントを用いて、以下の内容でメール送信APIを呼び出す。
   - `from`: 環境変数`RESEND_FROM_EMAIL`(基本設計書6.1節・6.2節の暫定運用/本番運用の値を切り替える)
   - `to`: 環境変数`CONTACT_RECEIVE_EMAIL`
   - `reply_to`: 入力された`email`(クライアントが返信しやすくするため)
   - `subject`: `[EIAI TECサイト] お問い合わせ(${name}様)`
   - `text` / `html`: `buildContactEmail`の戻り値
6. Resend APIの呼び出しが成功した場合、`{status:"success"}`を返却する。
7. Resend APIの呼び出しが例外(ネットワークエラー・4xx/5xxレスポンス)を返した場合、`try/catch`で捕捉し、詳細エラー内容をログに出力せず(PIIを含むため)、`{status:"error", message:"送信に失敗しました。"}`を返却する。詳細は8章参照。

### 4.10 F-08: モバイル用ナビゲーションメニュー

1. `MobileNavMenu`(クライアントコンポーネント、`"use client"`)が、`useState<boolean>`で開閉状態(`isOpen`)を保持する。
2. 開閉ボタンの`onClick`で`isOpen`をトグルする(`toggleMenu`)。
3. `isOpen`が`true`の場合、メニューパネル(4リンク)を描画する。ボタンの`aria-expanded`属性を`isOpen`の値に同期し、アイコンをハンバーガー/×に切り替える。
4. メニュー内リンクの`onClick`で、`isOpen`を`false`に戻す(`closeMenu`)。リンク自体は通常の`<a href="#xxx">`であり、アンカージャンプはブラウザ標準機能に委ねる。
5. 画面幅が640pxを超えた場合(リサイズでPC表示に戻った場合)は`isOpen`を`false`にリセットする。

### 4.11 F-09: 画像実ファイル化・next/image最適化

1. `images/`フォルダの5素材を`public/images/`(またはNext.js推奨の`app/`配下の静的アセットディレクトリ)に配置する。

### 4.13 F-11: Vercelデプロイ・独自ドメイン設定

1. Vercelプロジェクトを作成し、GitHubリポジトリ(`develop`/`main`ブランチ)と連携する。
2. 開発中はVercelが払い出す仮ドメイン(`*.vercel.app`)で動作確認する。
3. 環境変数(`RESEND_API_KEY` `CONTACT_RECEIVE_EMAIL` `RESEND_FROM_EMAIL`)をVercelのプロジェクト設定に登録する(Preview/Production環境それぞれ)。

## 6. データベース詳細設計

本サイトはDBを採用しない(基本設計書2.1節・5章参照)。テーブル定義・物理ER図は作成しない。

代替として、フォーム関連の型定義(TypeScript)を以下のとおり定める。

```ts
// types/contact.ts
export type ContactFormInput = {
  company: string;   // 任意。未入力時は空文字
  name: string;       // 必須
  email: string;       // 必須
  message: string;     // 必須
  honeypot: string;    // 空文字であることが期待値
};

export type ValidationResult =
  | { valid: true }
  | { valid: false; fieldErrors: Partial<Record<"company" | "name" | "email" | "message", string>> };

export type ContactFormResult =
  | { status: "idle" }
  | { status: "success" }
  | { status: "error"; fieldErrors?: Partial<Record<"company" | "name" | "email" | "message", string>>; message?: string };
```

## 7. API/インターフェース設計

### 7.1 Resend Emails API(外部インターフェース)

| 項目 | 内容 |
|---|---|
| エンドポイント | `POST https://api.resend.com/emails`(`resend` npm SDKの`resend.emails.send()`経由で呼び出し、エンドポイントを直接意識する実装は行わない) |
| 認証 | `Authorization: Bearer ${RESEND_API_KEY}`(SDKが自動付与) |
| リクエストボディ(主要項目) | `from`(環境変数`RESEND_FROM_EMAIL`)、`to`(環境変数`CONTACT_RECEIVE_EMAIL`)、`reply_to`(入力`email`)、`subject`、`text`、`html` |
| 成功レスポンス | `201 Created` 相当、`{ id: string }` |
| 失敗レスポンス | `4xx`/`5xx`、`{ name: string; message: string }`(SDKは例外としてスローする場合がある) |

### 7.2 Server Action インターフェース(内部インターフェース)

```ts
// app/actions/contact.ts
"use server";

export async function submitContactForm(
  prevState: ContactFormResult,
  formData: FormData
): Promise<ContactFormResult> {
  // 4.9.2節の処理フローを実装
}
```

- クライアント側(`ContactForm`)からは`useActionState(submitContactForm, { status: "idle" })`の形で呼び出す(React 19 / Next.js App Router標準パターン)。
- 代替案(将来、外部システムから直接お問い合わせを送信する要件が生じた場合): Route Handler(`app/api/contact/route.ts`)として`POST`ハンドラを追加する方式も選択可能。本イテレーションではServer Actionのみで要件を満たすため採用しない。

### 7.3 環境変数一覧(基本設計書5.2節の詳細)

| 変数名 | 型 | 必須 | 設定先 | 公開範囲 |
|---|---|---|---|---|
| `RESEND_API_KEY` | 文字列(Resend発行のAPIキー) | 必須 | `.env.local`(開発)/ Vercel環境変数(Preview・Production) | サーバーサイドのみ(`NEXT_PUBLIC_`禁止) |
| `CONTACT_RECEIVE_EMAIL` | 文字列(メールアドレス形式) | 必須 | 同上 | サーバーサイドのみ |
| `RESEND_FROM_EMAIL` | 文字列(`表示名 <メールアドレス>`形式) | 必須 | 同上 | サーバーサイドのみ |

`.env.example`には上記3変数のキー名のみを記載し、値は空文字またはダミー値とする(セキュリティチェック結果報告書11.1準拠)。

## 8. エラーハンドリング設計

| 発生条件 | 判定タイミング | 表示内容 |
|---|---|---|
| `name`/`email`/`message`のいずれかが未入力のまま送信 | クライアント側送信時(4.9.1節-4)、およびサーバー側再検証時(4.9.2節-3) | 該当項目の直下に赤字で「◯◯を入力してください。」(確定済み、基本設計書8章B-1) |
| メールアドレスの形式が不正 | 同上 | 「メールアドレスの形式が正しくありません。」(確定済み) |
| いずれかの項目が3.1節の最大文字数を超過 | 同上 | 「◯◯は最大◯◯文字までです。」(確定済み) |
| ハニーポット欄に値が入っている | サーバー側(4.9.2節-2) | 訪問者には通常の送信成功時と同一の表示を返す(判定ロジックを悟らせないため)。ログにも「スパム判定」等の記録は残すが、フィールド値そのもの(PIIになりうるため)は記録しない |
| Resend API呼び出し失敗(4xx/5xxレスポンス、ネットワークエラー、タイムアウト) | サーバー側(4.9.2節-7、`try/catch`) | フォーム上部(4.3節ステータス表示領域)に「送信に失敗しました。お手数ですが時間をおいて再度お試しください。」を表示(確定済み)。入力済みの内容は保持し、再送信可能な状態を維持する |
| Resend送信成功 | サーバー側(4.9.2節-6) | フォーム上部に「お問い合わせを受け付けました。担当より通常2営業日以内にご連絡いたします。」を表示(確定済み。機能仕様書F-06の「通常2営業日以内」の案内文言と整合) |
| `RESEND_API_KEY`等の環境変数が未設定・不正(サーバー構成ミス) | サーバー起動時/Server Action実行時 | 訪問者には上記「送信に失敗しました。」と同一の一般的な失敗メッセージのみを表示する。詳細なエラー内容(設定不備であること)はVercel Function Logsにのみ出力し、訪問者が入力したPII(氏名・メールアドレス・相談内容)は出力しない(セキュリティチェック結果報告書11.1準拠) |

- 成功/失敗メッセージの表示領域は、`aria-live="polite"`を付与したライブリージョンとして実装し、スクリーンリーダー利用者にも通知する(基本設計書7章アクセシビリティ方針、基本設計書4.3節)。
- クライアント側バリデーションエラー時は、最初のエラー項目に`focus()`を当て、`aria-invalid="true"`・`aria-describedby`でエラーメッセージと入力欄を関連付ける。
