### 指摘No.1 【緊急】コミットメタデータに個人のメールアドレスが含まれ、公開GitHub上ですでに閲覧可能

| 項目 | 内容 |
|---|---|
| 重大度 | **緊急** |
| 該当箇所 | 全8コミット(`05b6fd7`〜`f6c78c4`)のauthor/committerフィールド、およびローカル`git config user.email` |
| 種別 | 個人情報(個人のメールアドレス) |
| Git状態 | **コミット済み・push済み・公開中**(`origin/main`・`origin/develop`の全コミット) |

**内容**

ローカルGit設定の`user.email`に個人のメールアドレスが設定されており(実値は本書には記載しない)、本リポジトリの**全コミットのauthor/committer情報として記録されている**。リモートはpublicであるため、以下の経路で誰でも取得可能な状態にある。

- GitHubのコミット一覧・各コミット詳細ページ(`.patch` / `.diff` 形式で末尾にアドレスが露出)
- GitHub公開REST API(`GET /repos/{owner}/{repo}/commits`。認証不要でauthor.emailが返る)
- `git clone`によるリポジトリ全体の取得

本チェックにおいて、公開API経由で実際に当該アドレスが取得可能であることを**再現確認済み**である。

**リスク**

- v1.0で「ドキュメントに個人のメールアドレスを書かない」という是正を行った目的(公開リポジトリ経由でのPII漏洩防止)が、**この経路によって実質的に無効化されている**。ドキュメントから除去しても、同一の(または同系統の)個人アドレスがコミットメタデータ経由で公開され続けている。
- 加えて、公開されているGitHubアカウント情報と組み合わせることで、個人の特定が容易になる可能性がある。
- スパム・フィッシング・クレデンシャルスタッフィングの標的リスト化に利用されうる。特に、当該アドレスがお問い合わせフォームの受信先と同一である場合、サイト公開後の到達経路が二重に露出することになる。

**履歴に残っている旨の明記(重要)**

本件は**すでにpush済みであり、以下の点に留意が必要**である。

- 今後のコミット設定を変えても、**過去8コミットのメタデータは書き換わらない**。
- 履歴書き換え(`git filter-repo`等)を行い強制pushしたとしても、**GitHub側に残るキャッシュ・既存のフォーク/クローン・GitHub Archive等のミラー、および第三者が既に取得した複製からは削除できない**。「一度公開されたものは取り消せない」という前提で影響を評価する必要がある。
- したがって本指摘は「完全な消去」ではなく、**①今後の露出停止 ②既存露出の影響低減**の2段構えで対応すべきものである。

**是正案(いずれも本書作成者は未実施。実施可否の判断が必要)**

1. **【推奨・最優先/低リスク】今後のコミットの露出を止める**
   - GitHubの `Settings → Emails` で「Keep my email addresses private」および「Block command line pushes that expose my email」を有効化する。
   - 本リポジトリのローカル設定を、GitHubが払い出すnoreplyアドレスへ変更する。
     ```
     git config user.email "<ID>+<username>@users.noreply.github.com"
     ```
   - グローバル設定(`git config --global user.email`)も同様に変更し、他案件での再発を防ぐ。
2. **【判断が必要/破壊的】過去履歴の書き換え**
   - `git filter-repo --mailmap` 等でauthor/committerを一括置換し、`--force`でpushし直す。
   - **ただし前述のとおり完全な消去にはならず**、加えてコミットSHAが全て変わるためクローン済み環境との整合が壊れる破壊的操作である。**実施する場合はユーザーの明示的な許可が必須。**
   - 本リポジトリは公開直後・関係者1名・フォーク0件と推定されるため、書き換えのコストは比較的低い。実施するなら早いほど効果が高い。
3. **【代替案/最も確実】リポジトリの作り直し**
   - 現行リポジトリを削除(またはprivate化)し、noreplyアドレス設定済みの状態で新規リポジトリとして初期コミットからやり直す。メタ事例としての「開発プロセスの公開」を重視する方針(site-direction.md §2)と両立させるなら、公開する履歴を意図的に作り直す本案が最も安全である。
4. **【方針判断】そもそもpublicである必要があるかの再検討**
   - 「このサイト自体をAI駆動開発のメタ事例として公開する」方針(site-direction.md §2)上、リポジトリ公開には積極的な意義がある。ただしその場合、**リポジトリの全内容が公開前提の成果物である**という認識を全フェーズで徹底する必要がある。公開はデプロイ直前まで待ち、内容を精査してから公開に切り替える運用も選択肢となる。

### 指摘No.2 【要対応】`.DS_Store`が過去コミットに混入し、公開リモートに残存

| 項目 | 内容 |
|---|---|
| 重大度 | **要対応** |
| 該当箇所 | コミット `f2101e2`(`fix: update Hero section in website mock`)で追加、`1b364d8`(`docs: update README and .gitignore`)で削除 |
| 種別 | ローカル環境情報の意図せぬ露出(macOS Finderメタデータ) |
| Git状態 | **ワーキングツリー・最新コミットからは削除済み。ただし履歴には残存し、`origin/develop`へpush済み(公開中)** |

**内容**

macOSのFinderが生成する`.DS_Store`(6,148バイト)が`f2101e2`で誤ってコミットされていた。`1b364d8`で`.gitignore`への追加とあわせて削除されているが、**Gitの性質上、削除しても過去コミットのオブジェクトとして履歴に残り続ける**。`f2101e2`は`origin/develop`から到達可能であり、`git show f2101e2:.DS_Store`で誰でも取得できる。

**リスク**

- `.DS_Store`にはFinderの表示設定に加え、**そのディレクトリに当時存在したファイル・フォルダ名(Gitにコミットしていないものを含む)**が記録される。本件の該当ファイルを解析した結果、記録されていたのは`README.md`のみで、**未公開の機密ファイル名や個人情報の露出は確認されなかった**。実害は限定的である。
- ただし一般論として、`.DS_Store`は「コミットすべきでないローカル環境ファイルが混入した」ことを示す兆候であり、同種の事故が`.env`等で起きた場合は重大な結果を招く。今回は`.env`系ではなかったが、**運用上のプロセス不備の指標**として扱うべきである。

**是正案**

- `.gitignore`への`.DS_Store`登録は`1b364d8`で既に実施済みであり、現在のワーキングツリーの`.DS_Store`が追跡対象外であることを`git check-ignore`で確認済み。**今後の再発防止措置は完了している。**
- 履歴からの完全除去には`git filter-repo --path .DS_Store --invert-paths`等の履歴書き換えが必要だが、内容の機微度が低いことから、**指摘No.1の履歴書き換えを実施する場合に同時に処理するのが合理的**である。単独での書き換えは費用対効果が低い。
- 併せて、macOS環境ではグローバルgitignore(`git config --global core.excludesfile`)に`.DS_Store`を登録し、全リポジトリで再発を防ぐことを推奨する。

### 17.1 実装フェーズ(developer)への申し送り

v1.1の11.1(実装フェーズへの申し送り)は引き続き有効であり、**実装フェーズ着手時に必ず再読すること**。v1.3で新たに追加する事項は以下のとおり。

- **Resendアカウントの保護**: 基本設計書6.1節・B-2の方針により、Resendアカウントの登録メールアドレスと`CONTACT_RECEIVE_EMAIL`(=クライアントの受信先アドレス)が同一になる。当該アカウントが侵害されるとメール送信権限とAPIキーの両方が奪われるため、**強固なパスワードと二要素認証の設定**をアカウント作成時に必ず行うこと。
- **APIキーの権限を最小化する**: Resendのキー発行時に権限を選択できる場合は、送信に必要な最小権限(Sending access)のみを付与すること。
- **`.env.local`作成時の確認**: 初めて`.env.local`を作成した直後に`git status`を実行し、当該ファイルが未追跡として表示されないこと(`.gitignore`で除外されていること)を目視で確認すること。`.gitignore`の実効性は本チェックで検証済みだが、**実ファイル作成時の一次確認を習慣化する**。
- **`.env.example`のコミット時**: `.env.example`のみ`.gitignore`のホワイトリストで追跡が許可されている。コミット前に、値が空文字またはダミー値であり、実キー・実アドレスが混入していないことを必ず確認すること。
- **画面キャプチャを成果物に含める場合**: 本フェーズの`mobile-nav_*.png`は良好な例(ページ内容のみの切り出し、メタデータなし)であった。今後テスト結果報告書等でキャプチャを追加する場合も、**ブラウザのURLバー・タブ・ブックマーク・デスクトップ・通知が写り込まないよう範囲を限定**し、可能な限りメタデータを持たない形式で保存すること。特に**実際のフォーム送信テストの画面**をキャプチャする際は、入力したテストデータ・受信メール画面にPIIや実アドレスが写り込みやすいため、**ダミーデータを用いるか該当箇所をマスクすること**。
- **実装コードの初回コミット前チェック**: v1.1の11.2のとおり、Resend連携コードの初回コミット前に本チェックを再実施すること。実装フェーズでは、ドキュメントと異なり**認証情報のハードコーディングが混入しうる**ため、チェックの重要度が上がる。
