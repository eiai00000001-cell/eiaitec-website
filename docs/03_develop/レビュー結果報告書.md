## 4. 指摘事項一覧

### R-1: モバイルメニューが閉じている間もリンクがキーボードフォーカス可能

- 観点: バグ・不具合
- 重大度: 中
- 該当箇所: `frontend/components/MobileNavMenu.tsx`(55〜68行目)、`frontend/app/globals.css`の`.mobile-panel`定義(209〜230行目)
- 内容: `.mobile-panel`は閉状態のとき`max-height:0; overflow:hidden;`により視覚的に隠され、ルート要素に`aria-hidden={!isOpen}`が付与されている。しかし内部の`<a>`リンク自体には`tabIndex={-1}`等が付与されておらず、`display:none`や`hidden`属性でDOMから除外されてもいない。そのため、閉状態でもキーボードのTabキー操作でこれらのリンクにフォーカスが移動してしまう(フォーカスリングも`overflow:hidden`により見えない)。`aria-hidden="true"`を付与した要素の内部にフォーカス可能要素を残すことは、支援技術のアクセシビリティツリーとキーボードのフォーカス移動が食い違う既知のアンチパターンである。
- 推奨対応: 閉状態のときはパネル内のリンクに`tabIndex={-1}`を付与する(開閉時に切り替える)か、`hidden`属性やCSSの`inert`属性を用いて視覚的な非表示とフォーカス不可を一致させる。
- 対応状況: 対応済み(2026-09-12)。`MobileNavMenu.tsx`のパネル内リンクに、`isOpen`が`false`のとき`tabIndex={-1}`、`true`のとき`tabIndex`未指定(通常のフォーカス順)を付与するよう修正。`__tests__/components/MobileNavMenu.test.tsx`に閉状態/開状態でのtabIndexを検証するテストを追加し、全テスト成功を確認。

### R-2: トップページ全体の`force-dynamic`化が静的最適化方針とトレードオフになっている

- 観点: 設計整合性(非機能要件)
- 重大度: 中
- 該当箇所: `frontend/app/page.tsx`(12行目 `export const dynamic = "force-dynamic";`)。関連: `docs/02_architect/基本設計書.md` 7章(310行目「Vercelの静的最適化(可能なセクションはServer Componentとして事前レンダリング)」)、詳細設計書4.12節-3、README.md D-5(109行目)
- 内容: 動的コピーライト年(年に1回しか変化しない値)を最新化するためだけに、トップページ全体をリクエスト時レンダリング(`force-dynamic`)にしており、基本設計書7章が明記する静的最適化によるパフォーマンス改善方針を、ページ全体について実質的に放棄する結果になっている。README.md D-5は「Next.js App Routerの動的レンダリング設定はルート単位でしか指定できないため」とだけ説明しているが、`export const revalidate = <秒数>`によるISR(Incremental Static Regeneration、例えば1日単位の再検証)であれば、年が変わる程度の低頻度な更新要件を満たしつつ大部分を静的配信できるため、より低コストな代替手段が存在する。
- 推奨対応: 次回改修時に`revalidate`を用いたISRへの切り替えを検討する。年境界(1/1)をまたぐタイミングのみ表示が最大でrevalidate間隔分古くなる可能性があるが、個人事業主のLPというサイト特性上、実用上の影響は小さいと考えられる。
- 対応状況: 対応済み(2026-09-12)。`app/page.tsx`の`export const dynamic = "force-dynamic"`を`export const revalidate = 86400;`(1日単位のISR)に置き換え。`npm run build`実行結果で`/`ルートが`○ (Static)`かつ`Revalidate: 1d`と表示されることを確認し、静的最適化が有効になったことを確認済み。README.md D-5に変更内容を追記。

### R-3: eyebrowグループの基準セクションがコンポーネントのマウント順に暗黙依存

- 観点: コード品質
- 重大度: 低
- 該当箇所: `frontend/hooks/useEyebrowAutoScale.ts`(45〜67行目 `applyGroups`)、`frontend/app/page.tsx`(18〜33行目のセクション描画順)
- 内容: 詳細設計書4.2節-3は「Servicesの計算結果のフォントサイズを基準値とし、Portfolio/About/Contactのeyebrowフォントサイズをこの基準値で上書きする」と明記している。実装では、同じ`groupId`を持つインスタンスのうち「最初にレジストリ(Set)へ登録されたもの」を基準として採用しており、これは`app/page.tsx`でServicesが他の3セクションより先にマウントされることに暗黙的に依存している。この前提はコード上どこにも明示されておらず、テスト(`__tests__/hooks/useEyebrowAutoScale.test.tsx`)もテストハーネス内での登録順を検証しているのみで、実際の`page.tsx`の描画順とは結び付いていない。将来`page.tsx`のセクション順序を入れ替えた場合、テストが失敗しないまま基準セクションが無警告で変わってしまうリスクがある。
- 推奨対応: 「Servicesを基準とする」という設計ルールを、マウント順ではなく明示的なフラグ(例: `isReference: true`)や役割指定で表現する。あるいは、コードコメント・テストで「`page.tsx`でServicesを最初にレンダリングする前提」であることを明示し、退行を検知できるようにする。
- 対応状況: 対応済み(2026-09-12)。`useEyebrowAutoScale`に`isReference?: boolean`を追加し、`applyGroups`はグループ内で`isReference: true`のインスタンスを優先的に基準として採用する(未指定時は従来どおり最初の登録を基準とする後方互換フォールバック)よう修正。`EyebrowHeading`/`SectionHeading`/`SectionIconRow`経由でpropを伝播させ、`ServicesSection`に`isReference`を明示付与。`__tests__/hooks/useEyebrowAutoScale.test.tsx`を、マウント順に依存しないisReference指定での基準選択を検証するテスト、および未指定時のフォールバック挙動を検証するテストに更新。

### R-6: `next.config.ts`に開発者個人のLAN IPアドレスがハードコードされている

- 観点: コード品質
- 重大度: 低
- 該当箇所: `frontend/next.config.ts`(10行目 `allowedDevOrigins: ["192.168.1.2"]`)
- 内容: 開発サーバーをLAN内の他端末から確認するための設定として、開発担当者個人のLAN IPアドレスが直接コミットされている。コメントにも「IPが変わった場合(DHCP再割当等)は…書き換えること」とあり、運用が個人の開発環境に依存した状態になっている。基本設計書6.3節のとおり本リポジトリはpublicであるため、内部ネットワーク構成の情報(プライベートIPで実害は限定的だが)がコミット履歴含め公開される点も含め、望ましい状態ではない。なお本設定は開発時のみ有効で本番ビルドには影響しないため、重大度は低とした。
- 推奨対応: 各開発者のローカル環境変数(`.env.local`等、gitignore対象)から読み込む形にするか、値をより一般的なプレースホルダーにしてREADME等に「各自のLAN IPに書き換える」旨を案内する運用に変更する。
- 対応状況: 対応済み(2026-09-12)。`next.config.ts`のハードコードを廃止し、環境変数`DEV_ALLOWED_ORIGIN`(`.env.local`、gitignore対象)から読み込む形に変更。未設定時は`allowedDevOrigins: undefined`にフォールバックし、`npm run dev`/`npm run build`が壊れないことを確認済み。`.env.example`に変数名(値は空)を追記。
